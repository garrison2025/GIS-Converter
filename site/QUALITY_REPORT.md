# GIS Converter — Automated quality inspection (staging)

A local, **bounded structural comparison** is produced *inside* the existing conversion Worker before the GIS file is downloaded. All checks are browser-local, and the downloadable JSON is created through an in-memory Blob URL.

### Supported checks
- Independently parse recognized GeoJSON `FeatureCollection` objects, CSV rows with longitude/latitude, single-point KML Placemarks, simple GPX waypoints, KMZ KML contents, and zipped SHP/SHX/DBF metadata.
- Compare input vs output feature counts only when both inspectors can structurally account for their data.
- Compare WGS84 point bounds only when both coordinate systems can be inferred safely and geometry types are supported.
- Flag discrepancies as **Review** instead of manufacturing a green certificate. Return **Unavailable** for unknown projections, detailed GPX track geometry comparisons, complicated KML, mixed geometry cases and unsupported formats. For GPX→KML/KMZ, a narrower logical feature-count check is available.
- Report has no source feature properties, names, user files or personally identifying location details beyond a numeric bounding box, which is **local and can itself be sensitive**. The report is not uploaded automatically.

### Not certified
This is not a GIS data accuracy or security certification. It does not prove polygon topology, geometry repair, vertex-by-vertex equality, feature ordering, field names/types/value fidelity, styles, metadata, full reprojection quality, or safe handling of all malformed archives. A binary SHP index/DBF count check is necessary but insufficient. Only a small, explicit allowlist of GeoJSON WGS84/CRS84 declarations is recognized; any other declared CRS is not assumed to be WGS84. KML/GPX inspection is intentionally limited and uses a narrow simple-point recognition heuristic.

A conversion can succeed while the quality report requests review. Production GIS verification still requires independent QGIS/GDAL inspection of representative customer datasets. No user/account/payment service is active.

### P16 fail-closed protection
Mixed point/line/polygon GeoJSON geometry families are rejected before attempting a single Shapefile output. After conversion, if independent comparable feature counts or WGS84 point bounds definitively differ, the file is withheld and the user receives an error. Unknown or unsupported comparisons remain explicitly `unavailable`; they do not claim certification. The rule currently applies only where the independent parsers can compare those invariants. This cannot guarantee every feature or attribute survived.

### P17 Shapefile field compatibility warnings
For GeoJSON→Shapefile, the report scans source property **names and types** within a bounded set and warns about UTF-8 field names over 10 bytes, possible first-ten-byte collisions, or object/list properties. Only counts are exposed in the local JSON report, not source keys or values. A clean schema scan **does not prove field values are preserved**; Shapefile DBF has other field type/width restrictions. See GDAL's official ESRI Shapefile/DBF driver reference. The conversion is not withheld for metadata-name warnings alone.

### P20 GPX logical-layer protection and tested samples
- GDAL's GPX reader exposes three logical feature layers (`waypoints`, `routes`, `tracks`) plus two auxiliary vertex layers (`route_points`, `track_points`). Exporting only the logical layers to KML/KMZ prevents auxiliary vertices from being emitted as duplicate standalone point features.
- A browser-local independent `gpx-logical-features` check compares the count of source waypoints + routes + tracks against output KML Placemarks; an independently detected count mismatch withholds the download. Invalid or unsupported cases are not marked certified.
- Real Chromium/GDAL QA fixture: **2 waypoints + 2 routes + 2 tracks** (one track has two segments) yielded **6 Placemarks, 5 lines and 10 route/track vertices** in each of KML and KMZ. Names and each synthetic vertex coordinate are individually tested in the regression suite. This does not establish accurate preservation for every GPX extension, track-point time, elevation, large or malformed dataset.
- Independent sample EPSG:32650 UTM zone 50N Shapefile→GeoJSON roundtrip returned longitude/latitude within `0.0001°` of the WGS84 input. This is a single synthetic location and **not** general CRS certification.
- Two-record GeoJSON→Shapefile→GeoJSON QA checks UTF-8 Chinese strings, integer and decimal properties. DBF null values, arbitrary field names/types, widths and coercion remain **uncertified**. Do not infer production-safe attribute fidelity from the fixture.
- The production website remains a browser-local noindex engineering preview; billing is not activated. Cloudflare public deployment must be checked separately from GitHub CI.

### P21 track vertex checks and value compatibility warnings

- **GPX → KML/KMZ**: a bounded browser-only comparison inspects logical GPX route segments and track segments against output KML LineStrings. It compares total vertex counts, segment counts and within-segment lon/lat coordinates rounded to **six decimal places**. A definite discrepancy withholds the converted file. It is *not* an exact geodetic accuracy, full XML validity, ordering, elevation or topology certificate.
- The P21 line inspector deliberately returns **Unavailable**, rather than passing, for unsupported markup/invalid coordinates, waypoint-only GPX, more than 2,000 lines, 50,000 route/track vertices, or 4 Mi characters in either inspected XML string. Its exported JSON does not contain the source vertex list.
- GPX point-level <code>time</code>, <code>ele</code> and <code>extensions</code> tags produce an aggregate **Review** warning. The GDAL GPX driver exposes some of these on per-point auxiliary layers, but this product's KML/KMZ exports use the three logical feature layers. Do not assume timestamp, elevation or extension preservation; source samples are not included in the report.
- **GeoJSON → Shapefile**: count risky source values including explicit <code>null</code>, UTF-8 strings longer than 254 bytes, numbers with more than 15 significant decimal digits and unsafe integer values. These produce a **Review** warning; they do **not** automatically block a conversion or prove that a DBF truncation happened. The original values are not included in the report.
- Actual Chrome/GDAL tests cover a GPX with sample time/elevation values and a one-record long-string/null/precision DBF example. These are regression fixtures rather than independent certification of arbitrary customer datasets. Null roundtrip is **not** marked certified.
- Formal release still requires representative real-user files inspected with independent QGIS/GDAL. Live Pancake/Waffo billing, accounts, ads and SEO indexing remain disabled.

### P22 independently parsed Shapefile DBF values and fail-closed protection

- For **GeoJSON → Shapefile**, the conversion Worker independently reads the generated archive's .dbf and same-stem UTF-8 .cpg file. It validates DBF headers, record counts, column descriptors, record byte widths, and active row data before comparing eligible input GeoJSON properties.
- **Comparable fields** have unambiguous ASCII names of at most 10 characters, appear on every feature, and use supported DBF character (C) or numeric (N/F) values. UTF-8 strings and finite, reasonably precise numbers are compared by record order. Numeric tolerance is bounded by 1e-10 absolute / 1e-12 relative. The downloadable report contains only counts and status, never private names or values.
- For a safely comparable field disappearing, a value changing beyond tolerance, a record count changing, or an incompatible output type, the new **dbf-attribute-values** check returns Review and the Worker **withholds the download** as detected DATA_LOSS.
- Explicit null values, missing/unknown code-page metadata, unsupported names, sparse properties, unsupported DBF types, unsafe integer/high-precision numbers, and inspection size limits remain Unavailable or partial. A comparison pass certifies **only eligible fields**, not the entire dataset.
- Safety limits: 15 MiB GeoJSON, 24 MiB ZIP/DBF, 20,000 records and 128 fields. Non-GeoJSON sources and different targets are outside this inspector's scope.
- P22 adds nine independently constructed binary DBF regression cases and two real Chromium/GDAL cases for valid output and deliberately modified fields. These are engineering tests, not a universal Shapefile guarantee.
- GPX point-level time/elevation metadata is still not claimed losslessly preserved in KML/KMZ; P21 retains an explicit review warning. A real metadata-preserving export format would require separately designed semantics and validation.

### P23 reverse Shapefile validation and GPX elevation repair

- For **Shapefile ZIP → GeoJSON**, the Worker now independently reads the input DBF rows and UTF-8 code-page marker and checks eligible ASCII field names and compatible character/numeric values against the output FeatureCollection. A known dropped field, changed comparable value, numeric precision difference beyond tolerance, or changed row count is a **blocking** data-loss finding. Unknown DBF encodings, blank/null cells, unsupported field types, unsafe numbers and bounded data remain **Unavailable**; this is not a universal DBF certification.
- The same bounded DBF parser is shared by the forward GeoJSON→Shapefile and reverse Shapefile→GeoJSON inspectors, preserving independent field/record extraction from the GDAL conversion engine. Quality report text excludes original names and values.
- For **GPX → KML/KMZ**, the current browser GDAL build was verified *not* to output source elevation as KML Z solely by setting the documented ELE_AS_25D open option. P23 therefore applies a conservative browser-local post-processing step: source GPX numeric `ele` values are appended to matching KML coordinate tuples as Z only when a six-decimal longitude/latitude key has a unique altitude. Missing, ambiguous, unsupported or oversized XML remains unchanged; this is not a vertical-datum calibration.
- GPX time values are **not** embedded as native Google Earth `gx:Track` timelines by this release. Per-point timestamps and extensions remain explicitly **Review**. KML applications may not display altitude without appropriate altitude-mode settings; numeric Z retention does not guarantee visual height equivalence.
- P23 regression coverage includes eight independent synthetic DBF reverse-integrity scenarios and browser GDAL conversions of SHP→GeoJSON with two UTF-8 rows, a deliberate modified-field download block, and GPX KML/KMZ elevation samples. Full production deployment and live usage are independent verification tasks.

### P24 GPX timestamps via KML gx:Track

- **GPX → KML/KMZ:** after ordinary GDAL conversion and the P23 altitude repair, the local Worker may upgrade a uniquely matched KML `LineString` corresponding to a GPX **track segment** into a native Google Earth `gx:Track` geometry. It writes one canonical UTC `<when>` for every `<gx:coord>`, with the required `xmlns:gx="http://www.google.com/kml/ext/2.2"` root namespace. The source GPX must have an explicit, valid time on **every** point in the segment, with at least two points. The original route/waypoint features and partially timed or ambiguous track segments are not upgraded. Individual existing Placemark counts and GDAL track segmentation remain unchanged.
- Source altitude for fully elevated track segments is carried into the third `gx:coord` value when available. A segment with **no altitude at any point** uses the KML-required numeric Z value `0` solely as a coordinate syntax placeholder; it is **not** an assertion that the GPS measurement was 0 meters above sea level. Mixed elevation coverage remains an ordinary KML line, and no vertical datum or visual altitude mode is certified.
- Timestamp parsing accepts bounded ISO 8601 numeric UTC/offset timestamps with at most millisecond precision; invalid calendar days, incomplete time fields, multiple time elements, duplicate geometry signatures, source/output coordinate mismatch and unsupported XML shapes are not silently interpolated or guessed. KML/KMZ already containing a conflicting `gx` namespace is left unchanged. Invalid or out-of-range date-time values stay on the ordinary line with a review warning.
- The separate P24 `gpx-timed-track` browser-only quality check reads back `gx:Track` time and coordinate arrays and cross-checks them against supported source GPX segments. A definite mismatch in a generated timed track is a **blocking** DATA_LOSS failure. Non-upgraded tracks and uninspectable source material remain **Unavailable**, not falsely passed. The report exposes counts but no original timestamps or GPS coordinates.
- Google Earth supports `gx:Track` as a Google extension to KML 2.2; other KML implementations may ignore the extension. A single Placemark's `MultiGeometry` can contain individual track segments as `gx:Track` geometry, but cross-client rendering, point-level GPX extensions, full-waypoint timestamps, timing sub-millisecond fidelity, altitude display and live public Cloudflare deployment are outside this acceptance suite.
- Automated evidence includes seven dedicated synthetic P24 cases, additional invalid-date regression, and three real Chromium/GDAL quality cases (KML, KMZ and deliberately changed timestamp), plus all existing 19 format conversion routes and billing ledger offline tests. No live Pancake billing, ads, registration or search indexing changes are made.

### P25 long GPS track/timezone guardrails and device-format regression scope

- GPS time processing now validates the full wall clock before normalization: hours must be 00–23, minutes and seconds 00–59, and numeric timezone offsets no greater than UTC±14:00. Invalid calendar days, impossible UTC offsets, 24:00, and unsupported leap seconds stay on ordinary untimed KML geometry rather than becoming fabricated UTC timestamps.
- A complete-time GPX segment only becomes a KML gx:Track if its parsed timestamps are **nondecreasing**. Device clock resets or backward time jumps are not silently sorted, re-dated or interpolated. Repeated times in the same second are allowed as-is. Canonical UTC offset conversion is independently tested.
- All P24 XML processing caps still apply: the timed GPX and input KML source must each be at most 4 MiB, 2,000 track segments and 50,000 vertices. P25 adds a separate **post-expansion output cap** of 4 MiB: if enhanced gx:Track XML would be too large for the independent validator, the ordinary GDAL KML is retained and timestamp fidelity is not claimed.
- The `gpx-timed-track` readback result can only be **Pass** if every uniquely eligible complete-time source segment is verified in the output. A partial native time upgrade reports **Unavailable** and discloses the number of eligible-but-unverified segments. A confirmed mismatch in an actual gx:Track still blocks download. Neither partial/unavailable nor `gpx-vertex-metadata` review is labeled full metadata certification.
- P25 has deterministic **synthetic** GPS-export-shaped regression fixtures: Garmin-style GPX 1.1 extension elements such as heart-rate/cadence, timezone offsets, pauses, repeated same-second times, 100 multi-segment cases, and a 6,000-point standalone inspection. The actual browser GDAL/WASM suite converts a 24-segment, 1,920-point GPX to both KML and KMZ, plus one dense 3,500-point track to KML. QA independently counts XML gx tracks and timestamp/coordinate pairs and checks output integrity. These are **not** files captured directly from Garmin/Apple/Suunto devices; synthetic test timing must not be generalized as a production performance guarantee.
- Device-format structure references (not copied full GPS tracks): [Garmin Nuvi example in bulk_extractor](https://github.com/simsong/bulk_extractor/blob/e86383947ee016c825599887334cacf011736abf/src/scan_gps.flex) and [Bangle.js GPX exporter](https://github.com/espruino/BangleApps/blob/9fe678997d86dfabb5aadc5fba272b7d5897a340/apps/rungps/gpx_maker.js). The gx:Track time/coordinate format follows the [Google KML reference](https://developers.google.com/kml/documentation/kmlreference/).
- **Separate release gates remain:** authentic device GPX samples with consent and privacy-safe routes; visual playback in the Google Earth Pro desktop application; browser/mobile memory and long-file UX on actual devices; real Cloudflare Pages deployment. None is proven by GitHub CI alone. Live Pancake/Waffo billing, search indexing and advertising are still disabled.

### P26 real public GPX files, browser download integrity, and recovery

- **Three unchanged public GPX fixtures** are committed under `site/test-fixtures/public-gpx/`, with upstream source URLs, pinned source revision, attribution and the upstream Apache-2.0 license. The Garmin eTrex 20x-labelled public file has **104** timed/elevated track points; a Training Center-format sample has **9** timed points followed by an **empty segment**; a Runkeeper/Garmin-extension fixture contains one waypoint with heart-rate extension data. The source GPX `creator` attribute is *not* device-origin proof. These are public archival examples, unlike P25's independently generated synthetic long tracks.
- Browser GDAL/WASM regression checks the public eTrex file's 104 synchronized KML `gx:Track` timestamps and coordinates and compares `gpx-logical-features`, `gpx-line-geometry` and `gpx-timed-track` integrity checks. The empty-segment sample must not create additional vertices or omit recorded vertices; unsupported empty GPX geometry remains a **Review/partial** boundary rather than being called universally lossless. A waypoint with Garmin extension fields remains one `Point`, with no fabricated timed track.
- An actual **Playwright-driven Chromium click** downloads a GDAL-produced KMZ archive to a browser-managed file. The host runner independently computes SHA-256 and byte length of the downloaded file and compares them with the browser's original output. A separate repeated local long-track stress case performs three **3,500-point KMZ** conversions, reads Blob object URLs and compares their SHA-256 and size; it samples `performance.memory.usedJSHeapSize` only as **informational browser JS heap telemetry** (not resident RAM/RSS, mobile memory or a product performance guarantee).
- Failure recovery is validated by attempting to convert a malformed non-GPX file and then converting the same public real eTrex file with the **same initialized GDAL/WASM instance**, asserting 104 fully checked trajectory timestamps. Existing isolated Worker cancellation and input preflight suites still run separately.
- All cases run in CI's real **headless Chromium + GDAL/WASM** under Node/Playwright and local Wrangler, not in Apple Watch/Garmin/Suunto hardware or actual Google Earth Pro. Chrome JS-heap observations and lab conversion timing must not be represented as memory-performance guarantees on user devices. Actual Google Earth desktop playback and real Cloudflare Pages production deployment are still outside automated QA acceptance.
- The public files' source provenance and license details live in `site/test-fixtures/public-gpx/README.md`; no source GPS coordinate or clock string is included in published GIS quality reports. No Pancake/Waffo billing, production accounts, ads or indexing changes in P26.
